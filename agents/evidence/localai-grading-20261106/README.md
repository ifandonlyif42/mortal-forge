# localai 結果評估：依據、做法與回顧方式

建立日期：2026-11-06。對象：`~/.local/bin/localai`（不在 git repo 內；改前備份在 `~/.local/state/localai/localai.bak-20261106` 與 `localai.bak-20261106-grade`）。

## 為什麼要做

使用者看到本機模型吃記憶體，卻不知道是誰叫的、做什麼、做得好不好。原紀錄只有字數與秒數。因此新增三件事：每次呼叫必須寫目的、呼叫時列檢查項、完成後由監督者評成「完成／做到一半／失敗」。

## 找到的證據

| 主張 | 來源 | 我驗證到哪裡 |
| --- | --- | --- |
| 只看最後成敗看不出過程；可用「進度率」記錄逐步進展 | AgentBoard, Ma et al., NeurIPS 2024, https://arxiv.org/abs/2401.13178 | 2026-11-06 讀了摘要：有「fine-grained progress rate metric」與批評「mostly focus on the final success rate」。摘要沒有「部分完成」一詞；進度率等於子目標達成比例，是搜尋摘要的說法，未讀全文 |
| AI 當評審與人類一致率超過 80%，與人和人之間相當；有排序、冗長、偏好自己輸出的偏見 | Zheng et al. 2023, https://arxiv.org/abs/2306.05685 | 2026-11-06 讀了摘要，兩點都在摘要中 |
| 把評分拆成多個是否題，比量表分數穩定 | CheckEval（摘要頁 https://api.emergentmind.com/topics/checkeval）、Autorubric https://arxiv.org/html/2603.00077 | 只讀到搜尋結果摘要，未讀全文。結論只能當「有研究支持的方向」，不是已驗證 |
| 二元清單與量表打分在 agent 任務上的直接對比 | 無 | 查不到 |

沒採用：一份技能指南稱「先寫理由再打分可提升可靠度 15 到 25%」，沒有來源，不採用。

## 怎麼做

- `localai code|review|second` 必須附 `--why`（一句白話目的）與 2 到 5 個 `--check`（可用是或否驗證的檢查項），缺少即拒絕。
- 每筆紀錄多記：`run_id`、呼叫者（claude 或 codex 及程序編號）、repo、目錄、任務開頭 200 字、回覆開頭 300 字、檢查項。
- 完成後由監督者執行 `localai grade <run_id> --met N --total M [--note ...]`。判定規則：N 等於 M 為完成，N 為 0 為失敗，其餘為做到一半。評分以新的一行附加到紀錄，不改寫原紀錄。
- `localai now [--last N]` 顯示最近呼叫與其評估；未評估的會標出來。
- 評審者是呼叫的雲端監督者，不是本機模型，目的是避開自我偏好。

## 放棄了什麼

- 單一 1 到 10 分：量表容易飄，且與上述清單研究方向相反。
- 讓本機模型自評：論文列出自我偏好偏見。
- 自動打分：目前不做，人工或監督者逐項核對，避免把未驗證的 AI 評審當事實。

## 已跑的測試（2026-11-06）

- 缺少 `--check`、只給 1 項：皆被拒絕（結束碼 2）。
- 正常呼叫 `code` 一次（run id 20261106-101803-3412932），評為「做到一半 1/2」；`localai now` 正確顯示。
- `--met` 大於 `--total`：被拒（結束碼 2）；不存在的 run id：被拒（結束碼 1）。
- 沒跑：`review`、`second` 兩個角色的新路徑；多個工作階段同時寫 log 的競爭情況；超長輸入被拒時的紀錄內容。

## 已知弱點

- 檢查項由呼叫的 AI 自己列，可能列得太寬鬆；評審者與出題者是同一個，這是目前最大的盲點。
- 其他工作階段不知道新規則，第一次呼叫會被擋，須靠 `model-dispatch.md` 的規則文字讓它們學會。

## 回顧驗證（建議 2026-12-06 以後）

1. 有評估的呼叫占全部呼叫的比例。太低代表規則沒人遵守。
2. 「完成」的呼叫中，監督者事後標 `--outcome rejected` 的比例。高代表檢查項太寬鬆。
3. 抽 10 筆「完成」，人工重做檢查項，看是否同意。這是測評審是否可信，也是補上現在缺少的對照。
4. 若有足夠資料，比較「進度比例」與「最後是否被採用」是否相關，決定要不要留比例或改成純三級。

# 同一工作樹協作

同一工作樹共用實體檔案、Git 暫存區與目前分支；`git add` 記錄當下內容，之後改檔不會自動更新暫存區。不同工作樹各有檔案、HEAD 與暫存區，但共用部分倉庫資料與分支。OFFORA 訊息是協作紀錄，不是檔案鎖；本流程只能降低遵守規則的參與者之間的衝突，不能阻止其他程序或人員修改。`git worktree lock` 防止工作樹管理資料被清理，不是寫入互斥鎖。

## 開始前

1. 管理者查既有任務、工作者及未提交變更，保留他人工作；不把過去的路徑、AI 自述或辦公室畫面當作目前狀態。
2. 指定唯一管理者與唯一工作樹，記錄絕對實體路徑、共同 Git 目錄、工作樹 Git 目錄、分支及 HEAD。每個工作者在自己執行命令的環境核對 `pwd -P`、`git rev-parse --show-toplevel --absolute-git-dir --git-common-dir`、`git branch --show-current`、`git rev-parse HEAD` 與 `git status --short`；結果不符先停下。核對 `GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE` 等 Git 路徑覆寫環境；有不明覆寫先停下並釐清。不同容器或機器即使路徑相同也可能指向不同檔案系統：管理者建立一次性隨機識別內容，讓各工作者從指定位置讀回並比對，確認彼此看見同一份檔案；測試檔的建立與移除須納入明確授權。無法驗證共用檔案就停止派發寫入。不要只依名稱、相同 HEAD、Git 共用目錄或訊息判斷是在同一份檔案。
3. 確認 OFFORA 連線、身分與共用頻道；讀取任務相關訊息與後續訊息，依服務序號補讀。工具名稱和參數以實際可用工具為準；OFFORA 不可用、紀錄不完整或無法確認管理者時停止派發寫入，不假裝已協調。

## 派工與寫入

1. 管理者依依賴拆任務：前後依賴交由同一人連續處理或等前置完成；只有檔案與共享資源互不衝突的任務並行。先盤點格式化、程式產生、測試、快取、資料庫與設定等可能寫入的範圍。
2. 管理者在同一任務紀錄列出任務識別、工作樹、基準 HEAD、工作者、明確可寫路徑、共享資源、依賴、授權期限及驗收方式；路徑不得重疊，包含目錄與子路徑。管理者確認後回覆授權；工作者確認收到才寫入。未分配的檔案只能讀；需要擴範圍先停寫並取得新授權。期限或撤銷要求停止寫入，但不自動解除占用；此登記是合作約定，並非原子鎖。
3. 管理者是唯一 Git 寫入者，工作者不執行 `git add`、commit、切換分支、merge、rebase、reset、stash、restore、clean 或會改工作樹的 Git 操作。管理者也須先讓相關工作者停止寫入，核對範圍與現有暫存內容，再做被授權的操作；不可用全域加入或還原覆蓋別人的變更。
4. 工作者改檔前重新讀取現況；發現非預期變更、範圍重疊、指派不一致或失聯即停寫並回報，不自行覆蓋或接管。測試與格式化只可寫入本人授權的路徑及資源；會跨範圍時交管理者串行處理。
5. 工作者完成後停止寫入，回報實際檔案、測試、風險與是否有未完成程序；管理者自行核對差異，必要時記錄檔案雜湊並確認未再變動，再釋放或重新分配。訊息顯示離線、逾時或已讀不代表程序已停；無法確認原工作者及其子程序已停止就維持占用。管理者變更亦須先確認原管理者停寫並完整交接。

## 整合與驗收

管理者確認所有相關工作者已停寫，逐項核對實際差異與既有暫存內容，串行整合並執行跨任務驗收；分開檔案仍可能有介面依賴，因此以整合後版本重跑受影響檢查。提交時只加入已核對且獲授權的路徑，提交後檢查實際提交內容。報告已完成與未驗證部分，勿把派工、已讀或測試通過說成沒有其他寫入者或保證零衝突。高風險或無法確認所有寫入者遵守規則時，不在同一工作樹並行寫入。

參考：[Git worktree](https://git-scm.com/docs/git-worktree)、[Git add](https://git-scm.com/docs/git-add)、[Git 環境變數](https://git-scm.com/docs/git#_environment_variables)。

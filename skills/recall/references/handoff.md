# 交接模板與 PDF 輸入

這是人類的接手入口。用目前狀態寫，不抄聊天流水帳。沒有項目寫「無，已查哪些範圍」，沒查寫「未查證」。

## 接手文件

依實際任務填寫以下內容；檔案名保留專案原有約定。

| 內容 | 必須說清楚 |
| --- | --- |
| 目標與現況 | 要交付什麼、現在是否可用、盤點時間與範圍 |
| 已完成與可打開的成果 | 現在能做的事、入口、實測證據與限制 |
| 遺留與停點 | 未完成內容、影響、停下原因、下一個解除動作 |
| 從這裡接手 | 工作目錄、第一步、後續順序、操作命令或畫面、預期結果 |
| 現場整理 | 哪些已整理、哪些刻意保留、哪些待授權；未提交檔案的用途、背景工作與執行者、查看或接管方式 |
| 驗證方式 | 已跑／未跑檢查、驗證命令或人工操作、成功與失敗判準 |
| 已決定與不要重做 | 決定和理由、已失敗或已否決方向、完成後不用重跑的項目 |
| 查證資料 | 必要的原始證據連結，分開寫 Git、PR、CI、部署、真人驗收 |

成果在別的目錄或主機時，寫明從哪裡執行；不能只有一段無上下文的命令。待授權清理列出精確目標、原因與影響。

## PDF

從技能目錄執行：

```sh
python3 scripts/render_recall_pdf.py /絕對路徑/report.json /絕對路徑/report.pdf
```

JSON 的 `title`、`timestamp`、`summary` 和 `sections` 必填。每個 section 有 `heading` 及非空 `entries`；每個 entry 有 `title`、`detail`。`detail` 可含換行，長文字自動換行與分頁。`scope` 寫交接原件路徑及範圍，會完整排在最後。不要用完成百分比或大數字替代內容。

以下是假資料，只說明格式，不得當成真實完成證據：

```json
{
  "title": "工作交接",
  "timestamp": "2026-10-25 15:00 Asia/Taipei",
  "summary": "範例：預覽可開啟；匯出功能仍未完成。",
  "sections": [
    {"heading": "已完成與成果入口", "entries": [{"title": "範例預覽", "detail": "在專案目錄執行既有預覽命令，顯示主畫面；此處只是格式示範，未實跑。"}]},
    {"heading": "遺留與停點", "entries": [{"title": "匯出未完成", "detail": "尚未實作存檔，不能交付給使用者。"}]},
    {"heading": "從這裡接手", "entries": [{"title": "先確認預覽", "detail": "先讀交接原件的啟動方式，再檢查畫面。成功判準：主畫面出現；否則保留錯誤輸出。"}]},
    {"heading": "現場整理與驗證", "entries": [{"title": "保留未完成修改", "detail": "說明保留檔案的用途、程序狀態與未跑檢查，不自行刪除。"}]}
  ],
  "scope": "範例資料；真實交付應填入可打開的交接文件路徑。"
}
```

舊的 `metrics`、`statuses`、`work_summary` 輸入仍可重現舊報告；新交接一律使用 `sections`。PDF 是摘要，交接原件保存完整操作與證據；兩者內容必須一致。

維護排版程式時執行 `python3 scripts/test_render_recall_pdf.py`，檢查範例內容、長文分頁、空資料與舊格式。測試需 Cairo 與 Poppler；這些檢查不代表人類已能接手，仍需按實際交接操作並檢視 PDF。
